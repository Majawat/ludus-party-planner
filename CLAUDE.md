## Project Overview

**Ludus Party Planner** is a self-hosted web application for managing board game
nights and LAN party events. It handles event creation, attendee registration,
ticket management, seat assignment, loaner equipment, potluck coordination, and
game suggestions.

The operator runs approximately 2 events per year (one LAN party, one board game
weekend) with ~30 attendees max. The operator is a novice coder who needs to
maintain this long-term. Every decision optimizes for **readability and
maintainability over cleverness**.

---

## Non-Negotiable Constraints

- No frontend build process. No webpack, vite, npm for frontend assets.
- No frontend frameworks (React, Vue, Svelte). Server-rendered HTML only.
- All CSS and JS dependencies loaded from CDN.
- SQLite only. No PostgreSQL, no MySQL, no Redis.
- Everything runs in Docker via docker-compose.
- SSL and domain handled externally by a reverse proxy. Not in scope.
- The operator is the only admin initially. The system supports multiple admins
  via an `is_admin` flag on users.

## Tech Stack

| Layer | Choice | Rationale |
|---|---|---|
| Language | Python 3.12 | Readable, huge community, operator knows it |
| Framework | Flask | Explicit, minimal magic, easy to understand |
| ORM | Flask-SQLAlchemy | Standard, well documented |
| Migrations | Flask-Migrate (Alembic) | Schema must evolve safely |
| Auth sessions | Flask-Login | Handles session plumbing, well tested |
| Forms + CSRF | Flask-WTF | CSRF protection is not optional |
| Email | Flask-Mail | Simple SMTP wrapper |
| Password hashing | Werkzeug (built into Flask) | No extra install needed |
| Env vars | python-dotenv | Reads .env file |
| CSS framework | DaisyUI (via CDN, on Tailwind Play CDN) | Theming system, no build step |
| Interactivity | HTMX (via CDN) | Dynamic interactions without writing JS |
| Production server | Gunicorn | Replaces Flask dev server in Docker |
| Database | SQLite | Single file, fine at this scale |

### DaisyUI / Tailwind CDN Note
The Play CDN version of Tailwind is used (not production Tailwind). This is
acceptable for a low-traffic private site. The "not for production" label targets
high-traffic public sites. Do not suggest switching to a build step.

### HTMX Usage Pattern
Use HTMX for:
- Search boxes that filter results without page reload
- Inline check-in / mark-paid buttons in admin lists
- Any action where a full page reload would feel jarring

Do NOT use HTMX for everything. Standard form POST + redirect is fine for most
actions and easier to reason about. When in doubt, use a standard form.

### events
```
id                  INTEGER PK
name                TEXT NOT NULL
slug                TEXT NOT NULL UNIQUE     -- URL-safe, auto-generated from name, editable
type                TEXT NOT NULL            -- 'lan' or 'board_game'
status              TEXT NOT NULL DEFAULT 'draft'
                    -- 'draft', 'published', 'archived'
```

**Capacity is NOT stored on events.** It is computed as the sum of
`quantity_total` across active ticket types for the event.

**Available days** for ticket types are derived at runtime from
`start_datetime` / `end_datetime`. No separate days table.

### ticket_types
```
id                  INTEGER PK
event_id            INTEGER FK -> events NOT NULL
name                TEXT NOT NULL            -- "Weekend Pass", "Day Pass – Friday"
description         TEXT NULLABLE            -- Shown to user during registration
price               DECIMAL(10,2) DEFAULT 0.00  -- 0.00 for free
quantity_total      INTEGER NOT NULL
seatable            BOOLEAN DEFAULT FALSE    -- Does this ticket grant a seat?
includes_lodging    BOOLEAN DEFAULT FALSE    -- Does this ticket include a bunk bed?
valid_days          TEXT NOT NULL            -- JSON array of date strings: ["2026-03-06","2026-03-07"]
max_per_user        INTEGER DEFAULT 1
is_active           BOOLEAN DEFAULT TRUE     -- Admin can pause sales without deleting
created_at          DATETIME DEFAULT NOW
```

**quantity_sold is NOT stored.** It is computed:
`SELECT COUNT(*) FROM registrations WHERE ticket_type_id = ? AND status != 'cancelled'`

**Do not allow editing** `price`, `quantity_total`, or `seatable` on a ticket type
that has active registrations without a prominent warning in the UI.

## Key Design Decisions

Record these so they are never re-litigated:

**is_admin boolean, not a roles table**
Only two permission levels exist: admin and user. If a third level is ever
needed, add it then. Don't build a permissions system speculatively.

**Capacity computed, not stored**
`events` has no `capacity` field. Capacity = sum of `quantity_total` across
active ticket types. Always accurate, never out of sync.

**quantity_sold computed, not stored**
Count active registrations per ticket type at query time.

**valid_days as JSON text**
Stored as a JSON array of date strings on ticket_types. Generated from the
event's start/end date range in the admin UI (checkboxes for each day). No
separate days table.

**Seat availability computed, not stored**
A seat is taken if any non-cancelled registration has seat_id = that seat's id.

**One registration per user per event**
Enforced by UNIQUE(user_id, event_id) on registrations.

**No anonymous registrations**
Users must have an account to register for events.

**No friend registration**
One user registers themselves only. Not a current feature.

**Unverified users**
Can log in but see a persistent banner. Cannot register for events.
Unverified accounts older than 7 days should be cleaned up periodically.

**Day pass seat assignment**
Day pass holders do NOT pre-assign seats. First-come-first-served at the door.
Only seatable weekend pass holders claim seats in advance. (v1.1 may revisit)

**Sensitive config in env vars, display config in site_settings**
SMTP credentials, OAuth secrets, app secret key → .env
Site name, theme, social links, feature toggles → site_settings table

**Admin panel always uses data-theme="dim"**
Regardless of the ui_theme setting. Hard-coded in base.html for /admin/* routes.

**What to bring lives in description**
No separate `what_to_bring` field. Operators include it in the event description.

**Gallery is a URL, not file storage**
`events.gallery_url` links to Google Photos or similar. No file upload in scope.

**Email verification tokens and password reset tokens**
Always store hashed. Never store raw tokens in the database.

**checkin_code**
UUID generated at registration time. Used as a future QR code payload.
The scanner UI is v1.3 — the field is populated now.

## Bot/Spam Prevention

Two layers, both required:

1. **Honeypot field** on the register form. A hidden input (visually hidden via
   CSS class, NOT `display:none` or `type=hidden` — bots detect those).
   If the field has any value on submission, silently reject and show success
   (do not tell the bot it failed). No third-party dependency.

2. **Email verification required** before registering for events. Stale
   unverified accounts are the actual problem. The honeypot catches dumb bots;
   verification handles everything that gets past it.

Cloudflare Turnstile may be added later if needed. Do not add reCAPTCHA v2.

## Email

All email is sent via Flask-Mail using SMTP credentials from env vars.

**Transactional emails (MVP):**
- Email verification (sent on account creation)
- Password reset
- Registration confirmation (sent on successful event registration)

**Mass email (Phase 9):**
- Admin composes via /admin/email
- Selectable recipients (by event, filtered by payment status)
- HTML body accepted
- Respects newsletter_opt_in for non-transactional sends

Do not use background tasks (Celery, etc.) for email in MVP. Send inline.
If sending blocks, address it then.

## Coding Conventions

**Forms:** All form classes in `forms.py` using Flask-WTF. Always use
`{{ form.hidden_tag() }}` in templates for CSRF protection. Never build
forms without CSRF.

**Routes:** Standard POST-redirect-GET pattern for all form submissions.
After a successful POST, always redirect. Never render a template directly
after a POST that modifies data.

**Flash messages:** Use Flask's `flash()` for user feedback. Categories:
`'success'`, `'error'`, `'warning'`. Render in base.html.

**Admin guard:** Use a decorator on all admin blueprints. Never rely on
template-level checks alone to protect admin routes.

**Timestamps:** Store all datetimes as UTC. Display converts to local time
in templates if needed.

**Slugs:** Auto-generate from event name on creation. Allow admin to override.
Enforce uniqueness. Use hyphens, lowercase, no special characters.

**Migrations:** Always create a migration after changing any model.
Never modify the database schema directly.
Migration naming: `flask db migrate -m "short description of change"`

**Error pages:** Custom 404 and 500 templates using the site's theme.
Register handlers in `app.py`.

**No raw SQL:** Use SQLAlchemy ORM for all queries. Drop to raw SQL only
if there is a specific performance reason, and document why.

**HTMX responses:** Endpoints that serve HTMX requests should return HTML
fragments (partial templates), not full pages. Use `request.headers.get('HX-Request')`
to detect HTMX requests and return the appropriate template.

**JavaScript:** Minimize custom JS. Use HTMX for dynamic behavior where possible.
The only expected JS file is `seats.js` for seat selection UI.

**File uploads:** Not in scope for MVP. The `./static/uploads` volume is
mounted in Docker for future use. Do not implement file upload handling yet.

## Testing

### Stack
- `pytest` and `pytest-flask` — add both to `requirements.txt`
- Tests live in `tests/` at the project root
- Test database is always in-memory SQLite — never touches `data/ludus.db`

### Folder Structure
```
tests/
├── conftest.py          # Shared fixtures: test app, test db, test users, test events
├── test_auth.py         # Registration, login, email verification, password reset
├── test_events.py       # Event registration rules, capacity, guards
└── test_admin.py        # Admin guard, mark paid, check in, comp
```

### conftest.py Pattern
```python

from app import create_app
from models import db as _db

@pytest.fixture()

    app = create_app({

        "MAIL_SUPPRESS_SEND": True,      # Never send real emails in tests
        "SECRET_KEY": "test-secret-key",
    })
    with app.app_context():
        _db.create_all()
        yield app
        _db.drop_all()

@pytest.fixture()
def client(app):
    return app.test_client()

@pytest.fixture()
def admin_user(app):
    # Create and return an admin user

@pytest.fixture()
def regular_user(app):
    # Create and return a non-admin verified user

@pytest.fixture()

    # Create and return a published event with ticket types
```

### What to Test
Focus on paths where a silent bug would be catastrophic. Do not aim for
full coverage — test these specific things:

**Auth**
- Unverified users cannot register for events
- Verified users can log in
- Wrong password is rejected
- Password reset token expires and cannot be reused
- Honeypot field rejection on register

**Registration rules**
- User cannot register for the same event twice
- Cannot register when a ticket type is sold out
- Cannot register when `registration_open = False`
- Cannot register when `registration_closes_at` is in the past
- Confirmation email is triggered on successful registration

**Admin guard**
- Every `/admin/*` route returns 302 redirect for non-admin users
- Every `/admin/*` route returns 200 for admin users

**Admin actions**
- Marking a registration as paid updates `payment_status` and `paid_at`
- Marking as comped sets `payment_status = 'comped'`
- Check-in sets `checked_in_at`
- Cancelling a registration frees the seat and ticket count

### When to Write Tests
Write tests at the **end of each phase**, not during. Get the feature working
first, then lock it with tests before moving to the next phase. Do not let
testing block development momentum in early phases.

### Running Tests
```bash
pytest                        # All tests
pytest tests/test_auth.py     # One file
pytest -v                     # Verbose output
```

## Git and Development Workflow

### What Is Gitignored
```
.env                  # Never commit secrets
data/                 # Never commit the database (contains personal data)
__pycache__/
*.pyc
.venv/
venv/
static/uploads/
.DS_Store
```

`migrations/` is NOT gitignored. It is code — commit it.
`.env.example` is NOT gitignored. It documents required variables — commit it.

### Commit Conventions
- Commit at the end of each working feature, not each file save
- Every commit should leave the app in a working, runnable state
- Message format: imperative mood, short, descriptive
  - Good: `Add email verification flow`
  - Good: `Phase 3: Events read-only pages complete`
  - Bad: `wip`, `stuff`, `fix`

### Development Workflow
Two modes depending on context:

**Flask dev server** — use this during active development (90% of the time):
```bash
source venv/bin/activate
flask run --debug
```
Code changes reload instantly. No Docker rebuild needed. Runs on port 5000.

**Docker** — use this at the end of each phase and before any deployment:
```bash
docker compose up --build
```
Tests the full production-like stack. Runs on port 8000.

Never use `flask run` in production. Always use Gunicorn via Docker on the
home server.
